PR · worker  --proxy

借別人的 IP 繞 rate limit

Yahoo 按 IP 限流，多開機器很貴。這一章讓 worker 的爬取流量 改從一台雲端 VM 的 IP 出去——只加三行程式碼、VM 端零安裝、而且不動到 worker 連 server 的那條線。

worker.py README.md docs/worker-proxy.html

1為什麼需要這一步

revswarm 把 13.5 萬筆「股票 × 月份」的營收公布日爬回來，唯一來源是 Yahoo 搜尋。 痛點很直接——Yahoo 按來源 IP 限流：單一 IP 高頻查詢很快回小頁面、非 200， worker 就得退避長睡。既有解法是「多開機器 = 多 IP 分攤」，但為了換一顆 IP 而養一台完整 worker（要能連 server、要部署程式）成本偏高。

關鍵洞察：worker 其實有兩條互不相干的對外通道。 只有其中一條被 Yahoo 限流，另一條完全不該動。看懂這點，這個功能就只是「把其中一條改道」。

本機 worker（Python） Yahoo（被限流的目標） revswarm server
curl（fetch()）
爬 Yahoo 搜尋頁
→
tw.search.yahoo.com
← 這條會被限流
urllib（_req()）
租任務 / 回報
→

走 Tailscale，不該碰 proxy

所以目標很窄：只把 fetch() 那條 curl 改走一個外部出口，其餘一律不動。 出口用一台雲端 VM——但不想在 VM 上裝任何東西（連 Tailscale 都不裝）。

2出口怎麼來：SSH 動態轉發（SOCKS5）

不在 VM 裝東西，還要讓流量從它的 IP 出去，最乾淨的辦法是 SSH 動態埠轉發： VM 開機就自帶 sshd，本機用 ssh -D 在 127.0.0.1:1080 開一個 SOCKS5 代理，所有走它的請求都被 SSH 加密隧道 送到 VM，再從 VM 的 IP 出去。VM 端零安裝。

# 開一條 SOCKS5 通道到 VM（背景常駐；-N 不執行遠端指令、-f 丟背景）
ssh -D 1080 -N -f -o ExitOnForwardFailure=yes <user>@<VM_外部IP>

# 或用 gcloud（免手動貼公鑰、還能走 IAP，VM 可不開公網 IP）
gcloud compute ssh <VM> --zone <zone> -- -D 1080 -N -f -o ExitOnForwardFailure=yes
為什麼是 socks5h 而不是 socks5？ 尾巴那個 h 代表「hostname 也交給 proxy 解析」——連 DNS 查詢都在 VM 端做， 整條請求（含網域解析）都從 VM 出去。用 socks5 的話 DNS 仍在本機解， 雖然多半能通，但不是「完全從 VM 出」的乾淨語意。
socks5://
TCP 走 proxy，DNS 在本機解。出口 IP 對，但網域解析洩在本地。
socks5h://
TCP 與 DNS 都走 proxy。整條請求都從 VM 出——本章採用。

3程式碼：其實只有三處

難的是想通「只改一條通道」；真正的 code 極小。三處都在 worker.py， 節錄如下（highlight 行為本次新增）。

① 模組層讀一個環境變數

worker.py模組頂部
MIN_PAGE_BYTES = 2000        # 小於此視為被限流/擋（todo 2.6）
# 讓 curl 走 proxy（例 socks5h://127.0.0.1:1080，經 SSH SOCKS 從別的 IP 出去繞 per-IP# rate limit）。只影響爬 Yahoo 的 curl；worker↔server 的 urllib 不受影響、仍走原路。PROXY = os.environ.get("WORKER_PROXY") or None

② fetch() 把 curl 指令抽成 list，有 proxy 就附上

worker.py — def fetch()爬 Yahoo 的唯一出口
    cmd = ["curl", "-sS", "--http1.1", "-m", str(timeout), "-G",
           "-w", "\n%{http_code}",            # 末行附上 HTTP 狀態碼
           "https://tw.search.yahoo.com/search",
           "--data-urlencode", f"p={query}",
           "-A", UA,
           "-H", "Accept-Language: zh-TW,zh;q=0.9"]
    if PROXY:        cmd += ["--proxy", PROXY]              # socks5h:// → DNS 也在 proxy 端解
    try:
        r = subprocess.run(
            cmd,
            ...
        )

既有的 --http1.1 留著有原因：某些環境走 HTTP/2 會 SSL EOF、回 000。這跟 proxy 無關，但一起走 curl，所以照舊。

③ 一個 --proxy CLI 參數（也吃環境變數）

worker.py — def main()argparse
    ap.add_argument("--max-batches", type=int, default=0, help="跑幾批後結束(0=不限)")
    ap.add_argument("--proxy", default=os.environ.get("WORKER_PROXY"),                    help="爬 Yahoo 的 curl 走此 proxy，如 socks5h://127.0.0.1:1080…")
    args = ap.parse_args()

    global PROXY    PROXY = args.proxy or None
向後相容是設計目標。 沒設 WORKER_PROXY、沒帶 --proxy 時，PROXY 是 None，curl 一個字都不會多——舊行為原封不動。

4改動的邊界：只碰了「爬取」這一格

對照第 1 節那張「兩條通道」圖——這次的改動完全落在 worker 端、且只在 fetch() 這一格：

fetch() / curl
改：加 --proxy
→
走 VM 出口
✔ 本次目標
_req() / urllib
不動：租任務 / 回報
→
走原路（Tailscale）
✔ 完全不受影響

正因為 _req() 那條沒動，server 只在 tailnet（無公網）也照樣運作： worker 仍用 Tailscale 連 server，只有爬 Yahoo 那條繞到 VM。兩件事解耦。

5驗證：實測輸出逐行標注

以下都是這次開發真跑出來的輸出，不是想像的。

先證明通道確實換了 IP

本機：走 proxy vs 不走 proxy，各問一次「我的對外 IP 是多少」
$ curl -s --proxy socks5h://127.0.0.1:1080 https://api.ipify.org
35.229.164.167          ◐
$ curl -s https://api.ipify.org
61.219.173.229          ◑
  • 走 proxy 時對外 IP ＝ GCP VM 的 IP：流量確實從 VM 出去了。
  • 不走 proxy 就是本機真實 IP：兩者不同，證明改道成功、且沒設 proxy 時完全走原路。

再證明 worker 的 fetch() 真的能經 VM 抓到 Yahoo

設 WORKER_PROXY 後直接呼叫 worker.fetch()（不啟整個 worker）
$ WORKER_PROXY=socks5h://127.0.0.1:1080 python3 -c '…worker.fetch("台積電 2020年1月")…'
模組讀到的 PROXY = socks5h://127.0.0.1:1080     ①
ok = True | html 長度 = 136872              ②

$ python3 -c 'import worker; print(worker.PROXY)'   # 沒設環境變數
PROXY(no env) = None                            ③
  • 模組層確實讀到了環境變數 → 第 3 節 ① 那行生效。
  • ok=True 且頁面 136,872 bytes（遠大於 MIN_PAGE_BYTES=2000） → 經 VM 出口拿到正常的 Yahoo 搜尋頁，不是被限流的小頁。
  • 不給環境變數時 PROXY=None → 向後相容成立，舊部署不受影響。
讓通道自己活著。SSH 會斷。實務上把 ssh -D … 放進一個 while true; do … ; sleep 3; done 重連迴圈、跑在 tmux 裡（本專案慣例：長跑用 tmux 不用 nohup）。通道斷線期間 curl 會連不上 :1080 → worker 視為 rate_limited 退避，不會噴錯崩掉，通道回來就自動續爬。

6常見錯誤

用了 socks5://（少了 h）
後果 DNS 仍在本機解，語意不乾淨；少數環境會解析失敗或洩漏查詢。
正解 一律 socks5h://，把 DNS 也丟給 VM。
想把「連 server」也一起 proxy
後果 server 只在 tailnet 時，VM 根本連不到它 → worker 租不到任務。
正解 只 proxy 爬 Yahoo 的 curl；_req() 的 urllib 保持原路。
以為一台 VM 能無限換 IP
後果 一台 VM ＝ 一顆 IP；那顆被 Yahoo 標記後一樣會限流。
正解 要更多就多開 VM，各起一條通道輪流；或搭配多機 worker。
換了 IP 就把退避拿掉猛打
後果 新 IP 也很快被燒掉，還可能連累 VM 其他用途。
正解 退避照舊；換 IP 是「分攤」不是「加速轟炸」。
通道沒了自我修復就長跑
後果 SSH 一斷，整輪爬取全變 rate_limited 空轉。
正解 tmux + 重連迴圈 + ServerAliveInterval。
拿掉 --http1.1
後果 某些環境 HTTP/2 會 SSL EOF、回 000（與 proxy 無關的老坑）。
正解 curl 一律留 --http1.1。

7小結與下一步

這一步的精華不在 code（只有三行），而在看懂 worker 有兩條通道、只該改一條。 產物：WORKER_PROXY / --proxy，讓爬取從任意 SOCKS 出口出去， 向後相容、與 server 連線解耦。搭配一台雲端 VM 的 SSH SOCKS 通道，就能不多養 worker 而換一顆 IP。

目前限制（就是下一章的預告）

現在一次只吃一個 proxy——要真正規模化地分攤 Yahoo 限流，得多顆出口 IP 輪替 （多台 VM，或讓多機 worker 各自帶不同 --proxy）。輪替策略與健康檢查留待後續。

自我測驗 ①：為什麼 _req()（連 server）不能也走這個 proxy？

因為 server 常只在 tailnet（無公網 IP）。proxy 把流量從 VM 出去，而 VM 不在 tailnet， 根本連不到 server，worker 會租不到任務。限流的是「爬 Yahoo」那條，要改的也只有那條。

自我測驗 ②：沒設 WORKER_PROXY 也沒帶 --proxy 時會怎樣？

PROXY = None，fetch() 裡 if PROXY: 不成立， curl 一個參數都不會多加——行為與這次改動前完全一致（實測 ③ 印出 None）。

自我測驗 ③：實測看到 html 長度 = 136872，這數字證明了什麼？

證明經 VM 出口拿到的是「正常的 Yahoo 搜尋頁」，而非被限流的空/小頁面 （worker 以 MIN_PAGE_BYTES=2000 判斷；136872 ≫ 2000，所以 ok=True）。
