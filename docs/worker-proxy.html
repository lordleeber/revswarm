PR · worker  --proxy

借別人的 IP 出口：SSH SOCKS

把 worker 的爬取流量改從一台雲端 VM 的 IP 出去——只加三行程式碼、VM 端零安裝、 而且不動到 worker 連 server 的那條線。這是個乾淨、通用的技術…… 但我們當初是為了「繞 Yahoo rate limit」才做它,後來實測發現這個目的沒達成。

yahoo_worker.py README.md docs/worker-proxy.html

⚠️ 實測後記(請先讀)。 這章的 SSH SOCKS 機制本身正確且可重用,但它沒有解決我們原本要解的「一直被 rate limit」。 實測發現:VM 的 IP 並不比本機 IP 乾淨,兩者被擋的比率在雜訊內;真凶是 Yahoo 邊緣間歇回的 500 INKApi Error,解方是就地重試(PR #6),與換 IP 無關。 完整數據見文末 第 9 節・實測後記。以下照原始開發順序保留,當作 「先量測、別憑直覺」的教材。

1為什麼需要這一步

revswarm 把 13.5 萬筆「股票 × 月份」的營收公布日爬回來，唯一來源是 Yahoo 搜尋。 痛點很直接——worker 一直被判 rate_limited：查詢很快回小頁面、非 200， worker 就得退避長睡。我們當時的假設是「Yahoo 按來源 IP 限流」，既有解法是「多開機器 = 多 IP 分攤」，但為了換一顆 IP 而養一台完整 worker（要能連 server、要部署程式）成本偏高。

先劇透:這個「按 IP 限流」的假設是錯的。 但先照當時的思路走完(這正是本章的價值)——第 9 節會用數據推翻它。

關鍵洞察：worker 其實有兩條互不相干的對外通道。 只有其中一條被 Yahoo 限流，另一條完全不該動。看懂這點，這個功能就只是「把其中一條改道」。

本機 worker（Python） Yahoo（被限流的目標） revswarm server
curl（fetch()）
爬 Yahoo 搜尋頁
→
tw.search.yahoo.com
← 這條會被限流
urllib（_req()）
租任務 / 回報
→
你的 server
走 Tailscale，不該碰 proxy

所以目標很窄：只把 fetch() 那條 curl 改走一個外部出口，其餘一律不動。 出口用一台雲端 VM——但不想在 VM 上裝任何東西（連 Tailscale 都不裝）。

2出口怎麼來：SSH 動態轉發（SOCKS5）

不在 VM 裝東西，還要讓流量從它的 IP 出去，最乾淨的辦法是 SSH 動態埠轉發： VM 開機就自帶 sshd，本機用 ssh -D 在 127.0.0.1:1080 開一個 SOCKS5 代理，所有走它的請求都被 SSH 加密隧道 送到 VM，再從 VM 的 IP 出去。VM 端零安裝。

本機 worker 本機 SOCKS :1080 SSH 加密通道 GCP VM 出口 IP Yahoo
一次 fetch 的完整旅程
worker curl
--proxy socks5h://…
→
SOCKS :1080
127.0.0.1
→
SSH 通道
加密轉發
→
GCP VM
35.229.164.167
→
Yahoo
看到的是 VM 的 IP
本機（跑 worker 那台）shell
# 開一條 SOCKS5 通道到 VM（背景常駐；-N 不執行遠端指令、-f 丟背景）
ssh -D 1080 -N -f -o ExitOnForwardFailure=yes <user>@<VM_外部IP>

# 或用 gcloud（免手動貼公鑰、還能走 IAP，VM 可不開公網 IP）
gcloud compute ssh <VM> --zone <zone> -- -D 1080 -N -f -o ExitOnForwardFailure=yes
那 1080 是「在 VM 上開的 port」嗎？不是——它在本機。 -D 1080 是叫本機的 SSH client 在 127.0.0.1:1080 （loopback，外界連不到）開一個 SOCKS proxy。VM 端不 listen 任何新 port，全程只用它開機就有的 sshd（port 22）：SOCKS 收到的請求沿「既有那條 SSH 連線」送到 VM 的 sshd， 由 sshd 代替你向 Yahoo 發連線、從 VM 的 IP 出去。所以不必在 GCP 開任何防火牆規則， 也沒有服務被暴露到公網——只是「借 VM 的對外連線能力」，不是在 VM 上架一個對外服務。 （第 6 節有實測證據。）
為什麼是 socks5h 而不是 socks5？ 尾巴那個 h 代表「hostname 也交給 proxy 解析」——連 DNS 查詢都在 VM 端做， 整條請求（含網域解析）都從 VM 出去。用 socks5 的話 DNS 仍在本機解， 雖然多半能通，但不是「完全從 VM 出」的乾淨語意。
socks5://
TCP 走 proxy，DNS 在本機解。出口 IP 對，但網域解析洩在本地。
socks5h://
TCP 與 DNS 都走 proxy。整條請求都從 VM 出——本章採用。

3程式碼：其實只有三處

難的是想通「只改一條通道」；真正的 code 極小。三處都在 yahoo_worker.py， 節錄如下（highlight 行為本次新增）。

① 模組層讀一個環境變數

yahoo_worker.py模組頂部
MIN_PAGE_BYTES = 2000        # 小於此視為被限流/擋（todo 2.6）
# 讓 curl 走 proxy（例 socks5h://127.0.0.1:1080，經 SSH SOCKS 從別的 IP 出去繞 per-IP# rate limit）。只影響爬 Yahoo 的 curl；worker↔server 的 urllib 不受影響、仍走原路。PROXY = os.environ.get("WORKER_PROXY") or None

② fetch() 把 curl 指令抽成 list，有 proxy 就附上

yahoo_worker.py — def fetch()爬 Yahoo 的唯一出口
    cmd = ["curl", "-sS", "--http1.1", "-m", str(timeout), "-G",
           "-w", "\n%{http_code}",            # 末行附上 HTTP 狀態碼
           "https://tw.search.yahoo.com/search",
           "--data-urlencode", f"p={query}",
           "-A", UA,
           "-H", "Accept-Language: zh-TW,zh;q=0.9"]
    if PROXY:        cmd += ["--proxy", PROXY]              # socks5h:// → DNS 也在 proxy 端解
    for attempt in range(1, tries + 1):        # ← PR#6 後：就地重試
        html, retryable = _curl_page(cmd, timeout)   # 單次請求
        if html is not None:
            return html, True
        if not retryable:                        # 逾時：重試不划算，直接放棄
            break
        if attempt < tries:
            time.sleep(retry_sleep)             # 500 等秒回抽風才重試
    return None, False

既有的 --http1.1 留著有原因：某些環境走 HTTP/2 會 SSL EOF、回 000。這跟 proxy 無關，但一起走 curl，所以照舊。 （那個 for attempt 重試迴圈是後來 PR#6 才加的——它才是真正解決 rate_limited 的東西， 原因見 第 9 節；--proxy 這段留著無害但非解方。）

③ 一個 --proxy CLI 參數（也吃環境變數）

yahoo_worker.py — def main()argparse
    ap.add_argument("--max-batches", type=int, default=0, help="跑幾批後結束(0=不限)")
    ap.add_argument("--proxy", default=os.environ.get("WORKER_PROXY"),                    help="爬 Yahoo 的 curl 走此 proxy，如 socks5h://127.0.0.1:1080…")
    args = ap.parse_args()

    global PROXY    PROXY = args.proxy or None
向後相容是設計目標。 沒設 WORKER_PROXY、沒帶 --proxy 時，PROXY 是 None，curl 一個字都不會多——舊行為原封不動。

4改動的邊界：只碰了「爬取」這一格

對照第 1 節那張「兩條通道」圖——這次的改動完全落在 worker 端、且只在 fetch() 這一格：

fetch() / curl
改：加 --proxy
→
走 VM 出口
✔ 本次目標
_req() / urllib
不動：租任務 / 回報
→
走原路（Tailscale）
✔ 完全不受影響

正因為 _req() 那條沒動，server 只在 tailnet（無公網）也照樣運作： worker 仍用 Tailscale 連 server，只有爬 Yahoo 那條繞到 VM。兩件事解耦。

5實際怎麼跑起來（順序）

心智模型先擺正：通道是一個常駐的背景服務，不是你要一直開著的終端機。 把它跑在 tmux 裡（本專案慣例：長跑用 tmux），detach 後照樣活著——關掉終端機、甚至登出 SSH 都不影響。 worker 也是長跑，一樣丟另一個 tmux。所以是兩個 session：一個跑通道、一個跑 worker。

1
先起通道（若已在跑就跳過）——背景常駐、斷線自動重連。
本機tmux: socks
tmux new-session -d -s socks '~/rev-socks-tunnel.sh 2>&1 | tee -a ~/rev-socks.log'
2
確認通道通了再往下（走 proxy 應回 VM 的 IP，而非本機 IP）。
本機verify
curl -s --proxy socks5h://127.0.0.1:1080 https://api.ipify.org   # → 35.229.164.167
3
再跑 worker（另一個 tmux，帶上 WORKER_PROXY）。
本機tmux: worker
tmux new-session -d -s worker \
  'WORKER_PROXY=socks5h://127.0.0.1:1080 python3 -m worker.yahoo_worker --server http://<SERVER>:8000 --token <TOKEN>'
順序為什麼要緊？ worker 若在通道還沒起來時先跑，curl 連 :1080 會被拒 → worker 判定 rate_limited 退避（浪費時間，但不會崩）。通道自動重連，偶爾斷線 worker 會退避、 通道回來就自動續爬。所以「先通道、後 worker」不是硬規定，而是省掉開頭那段空轉。

6驗證：實測輸出逐行標注

以下都是這次開發真跑出來的輸出，不是想像的。

先證明通道確實換了 IP

本機：走 proxy vs 不走 proxy，各問一次「我的對外 IP 是多少」
$ curl -s --proxy socks5h://127.0.0.1:1080 https://api.ipify.org
35.229.164.167          ◐
$ curl -s https://api.ipify.org
61.219.173.229          ◑
  • 走 proxy 時對外 IP ＝ GCP VM 的 IP：流量確實從 VM 出去了。
  • 不走 proxy 就是本機真實 IP：兩者不同，證明改道成功、且沒設 proxy 時完全走原路。

再證明 worker 的 fetch() 真的能經 VM 抓到 Yahoo

設 WORKER_PROXY 後直接呼叫 worker.fetch()（不啟整個 worker）
$ WORKER_PROXY=socks5h://127.0.0.1:1080 python3 -c '…worker.fetch("台積電 2020年1月")…'
模組讀到的 PROXY = socks5h://127.0.0.1:1080     ①
ok = True | html 長度 = 136872              ②

$ python3 -c 'import worker; print(worker.PROXY)'   # 沒設環境變數
PROXY(no env) = None                            ③
  • 模組層確實讀到了環境變數 → 第 3 節 ① 那行生效。
  • ok=True 且頁面 136,872 bytes（遠大於 MIN_PAGE_BYTES=2000） → 經 VM 出口拿到正常的 Yahoo 搜尋頁，不是被限流的小頁。
  • 不給環境變數時 PROXY=None → 向後相容成立，舊部署不受影響。

順帶證明：VM 沒開任何 port，1080 只在本機

問 VM「有沒有人在聽 1080」＋看本機 1080 綁在哪個位址
$ gcloud compute ssh streaming-vm --zone=asia-east1-c --command="ss -ltn | grep -w 1080 || echo none"
[VM] 1080 沒有任何程式在聽                          ④
$ ss -ltn | grep -w 1080          # 這行是在本機看
LISTEN 0 128   127.0.0.1:1080   0.0.0.0:*            ⑤
  • VM 上沒有任何程式聽 1080——沒在 VM 開 port、沒動防火牆，只用了它既有的 sshd(22)。
  • 1080 只在本機，而且綁 127.0.0.1（loopback）→ 外界連不到，零暴露。
讓通道自己活著。SSH 會斷。實務上把 ssh -D … 放進一個 while true; do … ; sleep 3; done 重連迴圈、跑在 tmux 裡（本專案慣例：長跑用 tmux 不用 nohup）。通道斷線期間 curl 會連不上 :1080 → worker 視為 rate_limited 退避，不會噴錯崩掉，通道回來就自動續爬。

7常見錯誤

用了 socks5://（少了 h）
後果 DNS 仍在本機解，語意不乾淨；少數環境會解析失敗或洩漏查詢。
正解 一律 socks5h://，把 DNS 也丟給 VM。
想把「連 server」也一起 proxy
後果 server 只在 tailnet 時，VM 根本連不到它 → worker 租不到任務。
正解 只 proxy 爬 Yahoo 的 curl；_req() 的 urllib 保持原路。
以為一台 VM 能無限換 IP
後果 一台 VM ＝ 一顆 IP；那顆被 Yahoo 標記後一樣會限流。
正解 要更多就多開 VM，各起一條通道輪流；或搭配多機 worker。
換了 IP 就把退避拿掉猛打
後果 新 IP 也很快被燒掉，還可能連累 VM 其他用途。
正解 退避照舊；換 IP 是「分攤」不是「加速轟炸」。
通道沒了自我修復就長跑
後果 SSH 一斷，整輪爬取全變 rate_limited 空轉。
正解 tmux + 重連迴圈 + ServerAliveInterval。
拿掉 --http1.1
後果 某些環境 HTTP/2 會 SSL EOF、回 000（與 proxy 無關的老坑）。
正解 curl 一律留 --http1.1。

8小結（技術面）

純就技術而言，這一步的精華在看懂 worker 有兩條通道、只該改一條。 產物：WORKER_PROXY / --proxy，讓爬取從任意 SOCKS 出口出去， 向後相容、與 server 連線解耦。搭配一台雲端 VM 的 SSH SOCKS 通道，就能不多養 worker 而換一顆 IP。 這技術是對的、可重用的——只是它要解的那個問題，其實不是這樣解的（見下一節）。

自我測驗 ①：為什麼 _req()（連 server）不能也走這個 proxy？

因為 server 常只在 tailnet（無公網 IP）。proxy 把流量從 VM 出去，而 VM 不在 tailnet， 根本連不到 server，worker 會租不到任務。要改的只有「爬 Yahoo」那條。

自我測驗 ②：沒設 WORKER_PROXY 也沒帶 --proxy 時會怎樣？

PROXY = None，fetch() 裡 if PROXY: 不成立， curl 一個參數都不會多加——行為與這次改動前完全一致。

自我測驗 ③：既然換 IP 沒用，這章還留著幹嘛？

兩個理由：(1) SSH SOCKS 從固定出口出去是通用技術，日後真的需要換出口時直接可用； (2) 它是「憑直覺假設病因 → 花力氣做方案 → 一量測發現搞錯」的活教材。留著比刪掉有價值。

9實測後記：換 IP 沒用，真凶是邊緣抽風

做完 --proxy 後，實際一量測，假設就垮了。以下都是真跑出來的數據。

① 抓下失敗回應的 header——它根本不是「限流」

把回 500 的那次 response header 印出來
$ curl ... -D - -o /dev/null   # 走 proxy，dump headers
HTTP/1.1 500 INKApi Error
Server: ATS
Content-Length: 0
Connection: close
# 沒有 Retry-After、沒有 X-RateLimit-* → 不是標準限流(429/503)
  • Server: ATS = Yahoo 的邊緣 Apache Traffic Server；INKApi 是它內部 API(INK＝Inktomi 老代號)。所以這 500 是邊緣層自己出錯，不是後端限流你。

② 有節奏交錯測 20 輪：VM IP 沒有比較好

每輪 proxy 打一發、直連打一發，間隔 6 秒
PROXY (VM 35.229.164.167) : 200=14  500=6   成功率 70%
DIRECT(本機 61.219.173.229): 200=16  500=4   成功率 80%
  • 70% vs 80% 的差距在雜訊內；更關鍵的是逐筆看到同一查詢、同一秒，兩顆 IP 一起 500 → 這 500 綁的是邊緣/該次請求，不是來源 IP。換 IP 當然沒用。

③ 換個方向：就地重試——這才是解方

中 500 就地隔 2.5s 重試，看恢復率（直連 16 筆）
第一發就 200        : 13
第一發 500          : 3
  └ 重試 1 次就 200 : 3 / 3
不重試成功率 : 81%   →   加一次重試 : 100%  (16/16)
  • 500 是短暫抽風，重打一次幾乎必復原。真正的修正是在 fetch() 對非 200 就地重試（PR #6，即第 3 節那段 for attempt 迴圈），跟換 IP 無關。
這章真正的教訓。 「一直被 rate limit」聽起來像 IP 問題，直覺就想換 IP。但先量測才發現:它根本不是限流, 是 Yahoo 邊緣間歇性 500，換 IP 治不了、重試才治得了。方案做得再乾淨，解錯問題就是白做—— 先驗證病因，再動手。
那 --proxy 白做了嗎？不算。它本身正確、無害(未設時完全不生效)， 是可重用的「換固定出口」技術;只是別再拿它當繞 rate limit 的解方。proxy 通道(tmux socks) 平時可直接收掉。
